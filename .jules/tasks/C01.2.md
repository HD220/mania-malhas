**Descrição Detalhada:**

1.  **Listar Seções da Aplicação:** Identificar todas as seções principais da aplicação que possuem ou necessitam de layouts visualmente distintos ou estruturalmente diferentes (ex: cabeçalhos, rodapés, barras laterais, navegação).
    *   Exemplos atuais: `(admin)`, `(auth)`, `(main_app)`, `(marketing)`.
2.  **Documentar Requisitos de Layout por Seção:** Para cada seção, detalhar os componentes de layout específicos que são únicos ou compartilhados.
    *   O que muda? (Ex: Navbar principal vs. Navbar do admin)
    *   O que permanece? (Ex: Um wrapper global de tema)
3.  **Identificar Complexidades:** Notar quaisquer desafios de layout atuais ou desejados que são difíceis de gerenciar com a estrutura de layout existente.
4.  **Priorizar Necessidades:** Avaliar quais seções se beneficiariam mais imediatamente da aplicação de layouts distintos via Route Groups.

**Critérios de Aceitação:**
*   Um documento ou resumo claro dos requisitos de layout para cada seção principal da aplicação é produzido.
*   As diferenças e semelhanças entre os layouts das seções são claramente articuladas.
*   Potenciais pontos problemáticos ou áreas de melhoria com a estrutura de layout atual são identificados.

### Análise dos Requisitos de Layout (2024-08-09):

**1. Seções da Aplicação e Layouts Existentes:**
   - **`app/layout.tsx` (RootLayout Global):**
     - Fornece `<html>`, `<body>`, fonte Inter, `ThemeProvider`, `Toaster`. Envolve toda a aplicação.
   - **`app/(marketing)/layout.tsx`:**
     - Componentes: `MarketingHeader`, `MarketingFooter`.
     - Estrutura: Layout de página pública com header, conteúdo principal (container com padding específico), footer. Fundo `bg-gray-50`.
   - **`app/(auth)/layout.tsx`:**
     - Componentes: Nenhum específico; é um layout pass-through (`<>{children}</>`).
     - Estrutura: Minimalista, para páginas de autenticação controlarem seu próprio layout.
   - **`app/(admin)/layout.tsx`:**
     - Componentes: `AsideBar`, `Header` (admin), `Breadcrumbs`.
     - Estrutura: Layout de painel com sidebar e conteúdo principal (com padding).
   - **`app/(main_app)/layout.tsx`:**
     - Componentes: `MainAppHeader`, `MainAppFooter`.
     - Estrutura: Layout de aplicação principal com header, conteúdo (com padding), footer.

**2. Requisitos e Componentes por Seção:**
   - **Comum a todos (via RootLayout):** Estrutura HTML base, tema, sistema de notificações.
   - **Marketing:** Header e Footer específicos de marketing, layout de conteúdo centralizado.
   - **Auth:** Layout de página inteira, sem elementos de navegação compartilhados no nível do grupo de rota.
   - **Admin:** Sidebar de navegação persistente, header de admin, breadcrumbs.
   - **Main App:** Header e Footer específicos da aplicação principal, layout de conteúdo.

**3. Complexidades e Pontos de Atenção Identificados:**
   - **Uso de Múltiplos Layouts Raiz de Seção:** Cada grupo de rota principal (`(marketing)`, `(admin)`, `(main_app)`) efetivamente define um layout raiz para sua seção. O `(auth)` é uma exceção.
   - **Full Page Reload (Ressalva Next.js):** A navegação entre estas seções principais (ex: marketing -> admin) provavelmente já incorre em recargas completas da página. Isso é inerente ao uso de múltiplos layouts raiz distintos nos grupos de rota. O impacto na UX precisa ser considerado no contexto da frequência dessas transições. (Ref: Next.js docs, Issue #52879).
   - **Vazamento/Persistência de CSS Global (Ressalva Next.js):** A Issue #58597 do Next.js sugere que CSS global pode não ser removido corretamente ao transitar entre diferentes layouts raiz de grupos de rota.
     - O projeto usa `globals.css` (importado no RootLayout) e Tailwind. É preciso garantir que `globals.css` não contenha estilos que causem conflitos entre seções, ou que o comportamento de recarga realmente os limpe.
   - **Clareza da Estrutura:** A estrutura atual é uma aplicação padrão e válida de Route Groups para layouts distintos. A "viabilidade" mencionada em `C01` parece ser mais sobre otimizar ou resolver problemas com a implementação existente do que decidir sobre o uso inicial.

**4. Prioridades de Melhoria/Investigação (relacionadas a Route Groups e Layouts):**
   - **Investigar CSS Global:** Verificar se há vazamento de estilos de `globals.css` ou outros estilos globais introduzidos por layouts de grupo que causam problemas visuais entre seções.
   - **Avaliar Impacto do Full Page Reload:** Quantificar (se possível) e qualificar o impacto na UX das recargas completas entre seções.
   - **Consistência/Otimização:** Revisar os componentes de layout (`MarketingHeader`, `AdminHeader`, etc.) para garantir que são bem definidos, reutilizáveis e se há duplicação desnecessária.

**Conclusão para C01.2:**
   A análise básica dos layouts e seus requisitos está completa. Os principais pontos de atenção são o comportamento de recarga de página e o potencial vazamento de CSS global, que são características conhecidas (ou issues) do Next.js ao usar múltiplos layouts raiz com Route Groups.
