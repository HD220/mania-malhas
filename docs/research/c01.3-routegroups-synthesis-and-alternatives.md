## 1. Resumo dos Requisitos de Layout da Mania Malhas

A aplicação Mania Malhas identificou necessidades de layouts distintos para as seguintes seções:

*   **Seção Administrativa (`(admin)`):** Requer um layout com sidebar, header específico para admin e breadcrumbs. Esta necessidade é **confirmada** e já está implementada usando um Route Group com seu próprio `layout.tsx`.
*   **Seção de Autenticação (`(auth)`):** Requer um layout minimalista, focado no formulário de autenticação, sem elementos de navegação adicionais. Esta necessidade é **confirmada** e já está implementada usando um Route Group com um `layout.tsx` simples.
*   **Aplicação Principal (ex: `product/`, `partner/`):** Atualmente utiliza o `RootLayout` global. É **recomendado** um layout dedicado se esta seção for para usuários autenticados não-admin, para prover navegação e UX consistentes (ex: header com logo, navegação principal, menu do usuário).
*   **Páginas Públicas/Marketing (Potencial):** Se houver necessidade de páginas de marketing não autenticadas (landing pages, sobre, etc.), um layout distinto seria **essencial**, com navegação e estrutura totalmente diferentes. Esta necessidade precisa ser confirmada.

## 2. Capacidades dos Next.js Route Groups para Atender aos Requisitos

Next.js Route Groups são a ferramenta primária no App Router para organizar seções de uma aplicação e permitir que cada seção defina seu próprio layout raiz.

*   **Implementação:**
    *   Para a seção Admin: `src/app/(admin)/layout.tsx`
    *   Para a seção Auth: `src/app/(auth)/layout.tsx`
    *   Para a Aplicação Principal (se separada): `src/app/(app_core)/layout.tsx` (ou similar)
    *   Para Páginas Públicas/Marketing (se separadas): `src/app/(marketing)/layout.tsx` (ou similar)
*   **Benefício Principal:** Permitem uma clara separação da lógica de layout e da interface do usuário (UI) para diferentes contextos da aplicação. Cada grupo pode gerenciar seu próprio estado de layout, componentes e estilos de forma isolada.

## 3. Limitações e Considerações (Status das Capacidades Next.js)

A principal limitação ao usar Route Groups para definir múltiplos *root layouts* (ou seja, um `layout.tsx` diretamente dentro de cada Route Group no nível `app/`) é:

*   **Recarregamento Completo da Página (Full Page Reload):**
    *   Conforme documentado em C01.1, ao navegar entre rotas que pertencem a diferentes Route Groups com seus próprios root layouts (ex: de `/(admin)/dashboard` para `/(app_core)/products`), o Next.js executa um recarregamento completo da página.
    *   **Impacto na UX:** Perde-se a transição suave no lado do cliente (SPA-like) entre estas seções. O estado da aplicação no lado do cliente (ex: estado do React, scroll da página) pode ser perdido.
*   **Outras Caveats:**
    *   **Conflitos de Caminho de URL:** Rotas em diferentes grupos não devem resolver para o mesmo caminho de URL.
    *   **Layout Root de Nível Superior:** Se não houver `app/layout.tsx`, a rota `/` deve ser definida em um dos grupos.

## 4. Avaliação da Viabilidade e Recomendações

*   **Para as Seções Admin (`(admin)`) e Auth (`(auth)`):**
    *   Route Groups já estão em uso e são **adequados**.
    *   O recarregamento completo da página ao entrar/sair dessas seções é geralmente aceitável. Por exemplo, o login é uma transição natural que pode envolver um redirecionamento e recarregamento. A transição do app principal para o painel admin também pode ser vista como uma mudança de contexto significativa.
*   **Para a Aplicação Principal vs. Páginas Públicas/Marketing:**
    *   Esta é a área onde a limitação do full page reload é mais **crítica** se uma experiência SPA fluida for desejada ao transitar entre, por exemplo, uma página de produto (dentro da `(app_core)`) e uma página de blog (dentro da `(marketing)`).
    *   Se a "Aplicação Principal" (ex: `product/`, `partner/`) for para usuários autenticados e as "Páginas Públicas/Marketing" forem para visitantes não autenticados, a transição entre elas (ex: de uma página de marketing para o login, e depois para a aplicação) já envolve interrupções que tornam o full page reload menos problemático.
    *   O problema maior seria se, por exemplo, `(app_core)/products` e `(app_core)/orders` precisassem de layouts *fundamentalmente diferentes* (não apenas aninhados) e estivessem em Route Groups separados no nível raiz; a navegação entre eles sofreria full page reloads.

## 5. Alternativas (Se o Full Page Reload for um Bloqueador Significativo)

Se o recarregamento completo da página entre certas seções for inaceitável:

1.  **Layout Condicional dentro de um Único Root Layout:**
    *   **Descrição:** Utilizar um único `app/layout.tsx` (ou um layout principal para a área logada, ex: `app/(app_core)/layout.tsx`) que renderiza diferentes componentes estruturais (headers, sidebars, footers) condicionalmente, com base no pathname atual ou em algum estado da rota.
    *   **Prós:** Mantém transições SPA-like entre todas as seções cobertas por este layout.
    *   **Contras:** Pode tornar o arquivo de layout principal complexo e difícil de gerenciar. A lógica de layout fica centralizada em vez de distribuída.
    *   **Viabilidade:** Alta. É uma abordagem comum para variar elementos como o header em diferentes partes de uma SPA.

2.  **Estrutura de Componentes de Layout Aninhados (Layouts Padrão do Next.js):**
    *   **Descrição:** Priorizar o uso de layouts aninhados (`layout.tsx` em subpastas *sem* parênteses de Route Group no nível raiz). Os Route Groups no nível raiz seriam usados mais para organização de código ou para optar rotas *fora* de um layout compartilhado, em vez de criar múltiplos *root layouts* paralelos.
    *   **Prós:** Preserva transições SPA. É o comportamento padrão do Next.js para layouts.
    *   **Contras:** Menos flexibilidade se seções realmente precisam de HTML/body completamente diferentes no nível raiz (embora isso seja raro).
    *   **Viabilidade:** Alta. É a forma padrão de construir layouts no Next.js.

3.  **Aceitar a Limitação:**
    *   **Descrição:** Se a separação lógica e estrutural fornecida por Route Groups com root layouts distintos for mais valiosa, e os full page reloads entre seções principais (navegadas com menor frequência) forem aceitáveis.
    *   **Prós:** Máxima separação de concerns de layout.
    *   **Contras:** Impacto na UX para as transições afetadas.
    *   **Viabilidade:** Depende dos requisitos de UX do projeto.

## 6. Conclusão e Próximos Passos

*   Next.js Route Groups são eficazes para organizar rotas e definir layouts distintos para seções como `admin` e `auth`, onde o full page reload na transição para/de outras seções é geralmente aceitável.
*   Para a "Aplicação Principal" (ex: `product/`, `partner/`) e uma potencial seção "Pública/Marketing", a decisão de usar Route Groups no nível raiz para layouts completamente distintos deve considerar o impacto do full page reload.
    *   Se estas seções precisam de transições SPA entre si, alternativas como layout condicional ou layouts aninhados dentro de um grupo de rota principal (ex: `(app_shell)/layout.tsx` que então contém `(marketing)` e `(authenticated_app)` como sub-grupos ou pastas normais) devem ser consideradas.
*   **Recomendação Imediata:**
    *   Manter os Route Groups para `(admin)` e `(auth)` como estão.
    *   Para as demais funcionalidades (product, partner, etc.), se forem destinadas a usuários autenticados (não-admin), considerar agrupá-las sob um novo Route Group (ex: `(app_core)`) com seu próprio `layout.tsx`. Este layout forneceria o header e footer da aplicação principal. A transição entre `(admin)` e `(app_core)` teria um full page reload, o que é provavelmente aceitável.
    *   Se páginas de marketing/públicas forem necessárias, elas devem formar um novo Route Group (ex: `(marketing)`) com seu layout. A transição de `(marketing)` para `(auth)/login` e depois para `(app_core)` também envolveria full page reloads, o que é um fluxo natural.
*   O "bloqueio" mencionado na task C01 refere-se a este full page reload. Não é um bloqueio total, mas uma característica de design do Next.js com trade-offs que precisam ser avaliados. As alternativas listadas podem mitigar isso se necessário.

Este documento conclui a análise inicial sobre Route Groups e layouts distintos para o projeto Mania Malhas. As decisões de arquitetura subsequentes devem levar estas descobertas em consideração.
