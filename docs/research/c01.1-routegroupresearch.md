# Pesquisa sobre Next.js Route Groups para Layouts Distintos (C01.1)

Data da Pesquisa: 2024-08-01
Fonte Principal: [Documentação Oficial do Next.js sobre Route Groups](https://nextjs.org/docs/app/building-your-application/routing/route-groups)

## Resumo

A pesquisa sobre as limitações atuais e boas práticas de Next.js Route Groups para a implementação de layouts distintos foi realizada consultando a documentação oficial do Next.js (versões 13/14+).

## Convenção de Route Groups

*   Um Route Group é criado envolvendo o nome de uma pasta em parênteses: `(nomeDaPasta)`.
*   Esta convenção sinaliza que a pasta serve para fins organizacionais e **não** deve ser incluída no caminho da URL da rota.
    *   Exemplo: `app/(marketing)/about/page.js` será acessível como `/about`.

## Casos de Uso Principais

Os Route Groups são úteis para:

1.  **Organizar Rotas:** Agrupar rotas por equipe, funcionalidade ou qualquer outro critério lógico.
    *   Exemplo: `(marketing)` para rotas públicas, `(shop)` para rotas de e-commerce, `(admin)` para painel administrativo.
2.  **Definir Múltiplos Root Layouts:** Este é um caso de uso crucial para ter seções da aplicação com aparências e comportamentos completamente diferentes.
    *   Cada Route Group pode ter seu próprio `layout.js` na raiz do grupo (ex: `app/(shop)/layout.js` e `app/(marketing)/layout.js`).
    *   Isso permite que, por exemplo, a área de marketing tenha um layout e a área da loja virtual tenha outro, completamente independente.
3.  **Opt-in Seletivo de Layouts:** Permite que segmentos de rota específicos compartilhem um layout, enquanto outros, no mesmo nível ou em grupos diferentes, não o fazem.

## Caveats e Limitações Importantes

Ao usar Route Groups, especialmente para múltiplos root layouts, é crucial estar ciente das seguintes ressalvas:

1.  **Recarregamento Completo da Página (Full Page Load):**
    *   Se um usuário navegar entre rotas que utilizam *diferentes root layouts* (ou seja, layouts definidos em Route Groups distintos no nível raiz do `app`), o Next.js realizará um recarregamento completo da página.
    *   Exemplo: Navegar de `/cart` (usando `app/(shop)/layout.js`) para `/blog` (usando `app/(marketing)/layout.js`) resultará em um full page reload, não uma transição suave no lado do cliente (SPA-like).
    *   Esta é uma limitação significativa a ser considerada, pois impacta a experiência do usuário e a manutenção do estado da aplicação.
    *   Isso se aplica apenas a múltiplos *root layouts*. Layouts aninhados dentro de um mesmo root layout não causam esse efeito.

2.  **Caminhos de URL Conflitantes:**
    *   Rotas definidas em diferentes Route Groups não devem resolver para o mesmo caminho de URL.
    *   Exemplo: Ter `app/(marketing)/about/page.js` e `app/(shop)/about/page.js` é inválido, pois ambos tentariam corresponder à URL `/about`, causando um erro durante o build ou em tempo de execução.
    *   É necessário garantir que os caminhos de página sejam únicos em toda a aplicação, independentemente da organização em Route Groups.

3.  **Layout Root de Nível Superior (`app/layout.js`):**
    *   Se você estiver utilizando múltiplos root layouts (cada um em seu próprio Route Group) e **não** houver um `layout.js` global diretamente sob o diretório `app/`, é mandatório que a rota principal da aplicação (`/`) seja definida dentro de um dos Route Groups.
    *   Exemplo: Se não existir `app/layout.js`, a página inicial deve ser algo como `app/(marketing)/page.js` (para `/`) ou `app/(main)/home/page.js` (para `/home`, se `/` não for usado).
    *   Se um `app/layout.js` existir, ele será aplicado a todas as rotas, a menos que um Route Group no mesmo nível defina seu próprio root layout, o que levaria ao comportamento de full page reload ao transitar entre eles.

## Boas Práticas (Inferidas da Documentação)

*   Use Route Groups para separar logicamente grandes seções da sua aplicação (ex: `(public)`, `(admin)`, `(app_core)`).
*   Se múltiplos root layouts são necessários, esteja ciente da implicação do full page reload e comunique isso à equipe e stakeholders.
*   Planeje cuidadosamente sua estrutura de rotas para evitar conflitos de URL.
*   Para a maioria das aplicações, um único `app/layout.js` global combinado com layouts aninhados dentro de pastas normais (sem parênteses) pode ser suficiente e evita o full page reload entre seções. Route Groups com layouts próprios devem ser usados quando uma separação visual e estrutural radical é realmente necessária.

## Conclusão para a Tarefa C01.1

A pesquisa indica que Route Groups são uma ferramenta poderosa para organizar rotas e implementar múltiplos root layouts em Next.js. A principal limitação é o full page reload ao transitar entre rotas cobertas por diferentes root layouts. Boas práticas envolvem planejamento cuidadoso da estrutura de rotas e conscientização sobre essa limitação.
