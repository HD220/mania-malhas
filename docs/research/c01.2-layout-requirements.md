# Requisitos de Layouts Distintos na Aplicação Mania Malhas (C01.2)

Data da Análise: 2024-08-01
Task Referência: C01.2 - Identificar e documentar requisitos de layouts distintos na aplicação Mania Malhas.

## Introdução

Este documento detalha os requisitos de layout para as diferentes seções da aplicação Mania Malhas, especificamente as áreas `(admin)`, `(auth)` e as rotas principais da aplicação (referidas aqui como "Aplicação Principal / Pública Potencial"). A análise baseia-se na estrutura de arquivos existente e nas funcionalidades inferidas de cada seção.

## 1. Seção Administrativa (`src/app/(admin)/`)

*   **Propósito:** Fornecer uma interface coesa e funcional para usuários administrativos gerenciarem dados, configurações e monitorarem atividades na plataforma.
*   **Layout Existente:** `src/app/(admin)/layout.tsx`
*   **Componentes Chave do Layout Identificados:**
    *   `AsideBar`: Barra lateral persistente para navegação primária entre os módulos administrativos (ex: Dashboard, Produtos, Parceiros, Transações, Perfil, Notificações).
    *   `Header`: Barra superior contendo informações do usuário (menu de perfil, logout), possivelmente notificações e uma função de busca global dentro do admin.
    *   `Breadcrumbs`: Navegação secundária indicando a localização atual do usuário dentro da hierarquia administrativa, facilitando a orientação.
    *   Área de Conteúdo Principal: Espaço onde o conteúdo específico da página (formulários, tabelas de dados, painéis de visualização) é renderizado.
*   **Justificativa para Layout Distinto:**
    *   **Segurança e Acesso:** Isola funcionalidades administrativas de outras partes da aplicação, garantindo que apenas usuários autorizados tenham acesso.
    *   **Funcionalidade Específica:** Oferece ferramentas de navegação e interface (sidebar, breadcrumbs, header com controles admin) que não são relevantes ou apropriados para outras seções.
    *   **Experiência do Usuário (UX):** Proporciona um ambiente consistente e otimizado para tarefas de gerenciamento e visualização de dados complexos.
*   **Necessidade de Layout Distinto:** **Confirmada e já implementada.** O layout atual atende bem aos requisitos típicos de uma seção administrativa.

## 2. Seção de Autenticação (`src/app/(auth)/`)

*   **Propósito:** Oferecer uma interface clara, focada e segura para os processos de autenticação de usuários (login, registro, recuperação de senha, etc.).
*   **Layout Existente:** `src/app/(auth)/layout.tsx`
*   **Componentes Chave do Layout Identificados:**
    *   O layout é minimalista, primariamente renderizando os `children` (ex: formulário de login) dentro do `RootLayout`.
    *   Não adiciona componentes estruturais como sidebars ou headers complexos. A página `login/page.tsx` implementa um container flex para centralizar o conteúdo.
*   **Justificativa para Layout Distinto:**
    *   **Foco e Simplicidade:** Remove todos os elementos de navegação e distrações (sidebars, menus extensos) para concentrar o usuário na tarefa de autenticação.
    *   **Segurança:** Reduz a superfície de ataque ao não carregar componentes, scripts ou dados desnecessários para o processo de login/registro.
    *   **Branding:** Permite a exibição proeminente do logo da empresa e elementos de design consistentes com a identidade visual para páginas de entrada.
*   **Necessidade de Layout Distinto:** **Confirmada e já implementada.** O layout minimalista atual é apropriado para páginas de autenticação.

## 3. Aplicação Principal / Pública Potencial (Rotas em `src/app/*` fora de `(admin)` e `(auth)`)

*   **Propósito:** Esta seção atualmente inclui funcionalidades como listagem e criação de produtos (`src/app/product/`), parceiros (`src/app/partner/`), etc. Infere-se que seja a área principal da aplicação para usuários autenticados (não-admin) ou, potencialmente, para visitantes públicos (não autenticados) se algumas dessas áreas forem acessíveis publicamente (ex: catálogo de produtos).
    *   *Nota: A distinção entre uma área "pública para visitantes" (marketing, landing pages) e uma "área principal para usuários logados" não está explicitamente definida por um Route Group e layout dedicado atualmente.*
*   **Layout Existente:** Não há um layout específico para esta seção além do global `src/app/layout.tsx` (RootLayout). As páginas nesta seção (ex: `src/app/product/list/page.tsx`) são renderizadas diretamente dentro do `RootLayout`.
*   **Componentes Chave do Layout (Herdados do `RootLayout`):**
    *   Estrutura HTML básica, `ThemeProvider` para temas, `Toaster` para notificações.
    *   Não há um header de navegação principal consistente ou footer específico aplicado por um layout dedicado a esta seção.
*   **Requisitos Potenciais para um Layout Distinto (se esta seção for para usuários autenticados não-admin):**
    *   **Header Principal:**
        *   Logo da aplicação.
        *   Links de navegação para as funcionalidades chave da aplicação (ex: Produtos, Parceiros, Minhas Transações, etc.).
        *   Menu de usuário com acesso ao perfil e opção de logout.
    *   **Footer Principal:**
        *   Informações de copyright.
        *   Links para páginas informativas (ex: Termos de Serviço, Política de Privacidade), se aplicável.
    *   **Área de Conteúdo Principal:** Onde o conteúdo da página específica é renderizado.
*   **Requisitos Potenciais para um Layout Distinto (se fosse uma seção "Pública de Marketing" separada, ex: `(marketing)`):**
    *   **Header de Marketing:** Navegação focada em atrair visitantes (ex: Home, Sobre Nós, Funcionalidades, Preços, Blog, Contato, botões de Login/Cadastro).
    *   **Seções de Conteúdo Variadas:** Hero sections, calls-to-action, depoimentos.
    *   **Footer de Marketing:** Mais completo, com links de sitemap, redes sociais, informações de contato detalhadas.
*   **Justificativa para Layout Distinto:**
    *   **Para Usuários Autenticados (Não-Admin):** Criaria uma experiência de usuário consistente e logada, separada visualmente e funcionalmente do painel admin, mas mais rica que a de autenticação. Facilitaria a navegação pelas funcionalidades principais da aplicação.
    *   **Para Visitantes Públicos (Marketing):** Essencial para apresentar a marca, converter visitantes em usuários e fornecer informações gerais, com um design e navegação completamente diferentes de uma aplicação logada.
*   **Necessidade de Layout Distinto:**
    *   **Para a estrutura atual (ex: `app/product`, `app/partner`):** **Recomendado.** Se estas seções são para usuários autenticados (não-admin), um layout dedicado (ex: `src/app/(app_core)/layout.tsx` ou `src/app/(main)/layout.tsx`) melhoraria a navegação e a UX, fornecendo um header e possivelmente um footer consistentes.
    *   **Para uma futura seção de Marketing/Pública:** **Altamente Recomendado.** Se houver planos para páginas de landing, sobre, etc., estas deveriam residir em seu próprio Route Group (ex: `(marketing)`) com um layout totalmente distinto.
*   **Observação:** A tarefa C01.2 visa identificar quais seções *precisam* de layouts distintos. `Admin` e `Auth` já os possuem e são necessários. A área restante da aplicação se beneficiaria de um layout mais específico do que o `RootLayout` global, dependendo do seu público-alvo (usuário logado vs. visitante).

## Conclusão

1.  **Admin:** Layout distinto é necessário e já existe.
2.  **Auth:** Layout distinto é necessário e já existe (minimalista).
3.  **Aplicação Principal (ex: `product/`, `partner/`):** Atualmente usa o `RootLayout`. Um layout dedicado para esta seção (para usuários autenticados não-admin) é **recomendado** para melhorar a consistência e UX.
4.  **Páginas Públicas/Marketing:** Se houver necessidade de páginas de marketing/landing pages não autenticadas, um Route Group e layout distintos para elas seriam **essenciais**. Esta necessidade precisa ser confirmada.
